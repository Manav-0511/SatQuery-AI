# SatQuery AI - Specialist Execution & Trace

This document describes the orchestration of specialists in Phase 3. The `Executor` is responsible for taking a `SpecialistCandidateInfo` generated by the Router, instantiating the specialist via the `SpecialistRegistry`, and securely running it while generating an `ExecutionTrace`.

## Executor Responsibility

The `Executor` bridges the gap between the routing layer and the ML specialist layer. It:
1. Validates that the specialist can handle the request.
2. Invokes the `analyze()` method on the `BaseSpecialist`.
3. Handles all exceptions gracefully.
4. Generates an observable sequence of trace steps (`ExecutionTrace`).
5. Validates and returns the normalized `ExecutionResult`.

## Difference between SpecialistResult and ExecutionResult

- **SpecialistResult**: The strict contract returned by the ML model via the adapter. Contains the task, answer, evidence, confidence, and model provenance.
- **ExecutionResult**: The orchestration wrapper generated by the agent. It contains the `SpecialistResult` (if successful), plus the `ExecutionTrace`, internal system errors, timings, and orchestration lifecycle status (`RunStatus` or `FailureStatus`).

## Trace Semantics

An `ExecutionTrace` is a list of observable `TraceStep` records. A typical successful trace contains:
1. `INPUT_VALIDATION`
2. `QUERY_INTERPRETATION`
3. `TASK_SELECTION`
4. `SPECIALIST_SELECTION`
5. `SPECIALIST_EXECUTION_STARTED`
6. `SPECIALIST_EXECUTION_COMPLETED`
7. `RESULT_VALIDATED`
8. `EXECUTION_COMPLETED`

Trace steps deliberately **avoid** generating hidden chain-of-thought logic. Only observable systemic actions are logged.

## Error Handling

The Executor wraps specialist execution in a robust `try-except` block.
- If the specialist raises an exception, the system catches it, logs the error internally, and returns `SPECIALIST_FAILED`.
- If the specialist returns a malformed output (not compliant with `SpecialistResult`), the system rejects it as `INVALID_SPECIALIST_RESULT`.
- If the specialist cannot be found in the registry, it returns `SPECIALIST_UNAVAILABLE`.

## Provenance and Evidence Preservation

The executor relies on the specialist to return evidence.
- It **never** invents or fabricates evidence (like bounding boxes or masks). If a specialist returns `evidence: []`, it is kept empty.
- `Provenance` (like `is_real_data`, `synthetic`, `dataset`, `checkpoint`) is preserved exactly as returned by the specialist.
